22 Packages

Modules put one program into several files. A package lets a program use files that are not its own: a folder of modules that lives somewhere else. It may be beside the program, in somebody else’s git repository, or in the registry, where a package is found by its name alone.

22.1 Starting a program with zeno new

zeno new makes a folder with a small program in it, laid out the way a program that grows will want:

$ zeno new weather
Made the program `weather` in weather/
  zeno.package   the name of the program, and the packages it needs
  main.zeno      the program
  greeting.zeno  a module, with a test
Run it with `zeno run weather/main.zeno`, and its tests with `zeno test weather`.
$ zeno run weather/main.zeno
Hello, world, from weather.
$ zeno test weather
weather/greeting.zeno
  ok      hello says who it greets

1 test: 1 passed, 0 failed.

zeno new --package name makes a package instead: a folder of modules for other programs to use, with no main.zeno.

22.2 The project file

A folder is a package when it holds a file called zeno.package. The one zeno new made is comments, which say what can be written, and then one line:

weather/zeno.package

package weather

These are the lines there are, and that is all the file can say:

Line Means
package weather the name of this package
needs filters in "../filters" it needs the package in that folder, counted from this file’s folder. Nothing is copied
needs units at "v1.2.0" it needs that version of the package the registry calls units
needs units from "address" at "v1.2.0" it needs the package in that git repository, at that tag, branch or commit
about "Filters for noisy readings" what the package is for, in one line. A package needs it to be published
registry "address" look names up in that registry, and not in Zeno’s own
memory owned how the program frees memory: owned (one owner for each value, no collector) or collector, which is what it gets with no line (Memory)

A comment starts with #, as in a program. A program with no zeno.package is still a program; the file is needed from the day the program needs a package.

22.3 A package beside the program

Here is a package of filters for noisy readings, in a folder of its own:

filters/zeno.package

package filters

filters/filters.zeno

function mean(values: list[float]) -> float {
    return sum(values) / float(len(values))
}

function clamp(x: float, low: float, high: float) -> float {
    if x < low {
        return low
    }
    if x > high {
        return high
    }
    return x
}

filters/lowpass.zeno

from filters import clamp

class Lowpass {
    weight: float
    value: float

    function add(self, reading: float) -> float {
        self.value += self.weight * (reading - self.value)
        return self.value
    }
}

function start(weight: float, first: float) -> Lowpass {
    return Lowpass(clamp(weight, 0.0, 1.0), first)
}

And a program, in the folder beside it, that needs the package:

thermostat/zeno.package

package thermostat

needs filters in "../filters"

thermostat/main.zeno

import filters
import filters.lowpass

let readings = [18.2, 18.9, 19.6, 21.0, 22.4, 23.1]
let smooth = filters.lowpass.start(0.5, readings[0])
for r in readings {
    print(f"read {r:5.1f}  smoothed {smooth.add(r):5.1f}")
}
print(f"mean {filters.mean(readings):.2f}")
$ zeno run thermostat/main.zeno
read  18.2  smoothed  18.2
read  18.9  smoothed  18.5
read  19.6  smoothed  19.1
read  21.0  smoothed  20.0
read  22.4  smoothed  21.2
read  23.1  smoothed  22.2
mean 20.53

Which file an import names

The rule for imports has one step more than in the last chapter:

  1. If the first word of the import is a package that this file’s zeno.package needs, the rest is a file in that package’s folder. import filters.lowpass is lowpass.zeno there, and import filters alone is the file with the package’s own name, filters.zeno.

  2. Otherwise it is a file of the package the importing file is in.

Inside the package the same rule holds from the package’s own side: lowpass.zeno writes from filters import clamp to get its neighbour. A package sees its own files and the packages its own zeno.package needs, and nothing of the program that uses it, so the same package works in every program, and can be run and tested on its own.

22.4 Other people’s packages: zeno fetch

A package that somebody else keeps is in a git repository of theirs. The short way to need it is by its name:

package logger

needs units at "v1.2.0"

The name is looked up in the registry, which is new in Zeno 0.5.2: a list that says, for each name, which repository the package is and which commit of it each version is. zeno search shows what the registry has, and under each package the line to write:

$ zeno search lengths
1 package in the registry https://github.com/zeno-src/packages:

units v1.2.0    Lengths, masses and times that the checker keeps apart
    needs units at "v1.2.0"
    https://github.com/someone/zeno-units
    older: v1.0.0

The same list, with a box to search it, is at https://zeno-lang.org/packages/.

A package that is in no registry is named by its repository:

needs units from "https://github.com/someone/zeno-units" at "v1.2.0"

In this line at is a tag, a branch or a commit of that repository. In the line with only a name it is a version, which is written as the letter v and three numbers. In neither are there ranges such as ^1.2: the version written is the version used. Then, in the program’s folder:

$ zeno run main.zeno
error: the package `units` has not been fetched: there is no file
`packages/units/zeno.package`. Run `zeno fetch` in the folder of the program

$ zeno fetch
Asked the registry https://github.com/zeno-src/packages
Fetched units v1.2.0 (1c4e326) into packages/units
Fetched prefix v1.0.0 (d4461d9) into packages/prefix
Wrote zeno.lock

$ zeno run main.zeno
42.0

Four things happened.

  • Running never fetches. zeno run, check and build read files and nothing else. Only zeno fetch gets packages, with the git that is on the machine.

  • The registry was asked once, for the names that had no address. A line that names its repository does not need it.

  • What a package needs comes too. units needs prefix, so that was fetched as well. All of them go into one folder, packages/, beside the program’s zeno.package, and a program has one package of each name.

  • zeno.lock was written. It holds the repository and the exact commit of each package. A branch moves, but the next zeno fetch, here or on another machine, gets the commit in the lock, and asks no registry to find it. zeno fetch --update looks every version up again and writes the lock afresh.

Keep zeno.package and zeno.lock with the program. The folder packages/ can be made again from them at any time.

A range such as ^1.2 means the program built today and the program built next month may hold different code, chosen by somebody else’s release. Firmware that passed its tests on the bench must build the same a year later. One exact version and a lock file give that, and there is no solver to understand. Fetching only when asked means a build never depends on the network, which a factory build machine may not have. (Decisions 8.4, 8.9 and 8.10.)

22.5 The registry, and publishing to it

The registry is not a server. It is a git repository, https://github.com/zeno-src/packages, with one small file for each package. This is the file for units:

package units
about "Lengths, masses and times that the checker keeps apart"
from "https://github.com/someone/zeno-units"
owner "someone"

version "v1.0.0" commit "0123abc..." dated "2026-11-02"
version "v1.2.0" commit "9f8e7d6..." dated "2026-11-18"

The package itself stays in its author’s repository. The registry says where that is, and which commit each version is. zeno fetch checks out that commit, so a version that has been published stays what it was, even if somebody moves the tag afterwards.

To publish a package of your own, it needs three things: a git repository of its own that anybody can fetch from, an about line in its zeno.package, and a tag on the commit that is the version.

package filters
about "Filters for noisy readings"
$ git tag v1.0.0
$ git push origin main v1.0.0
$ zeno publish
`filters` v1.0.0 (32a7444) is ready to be published, from https://github.com/someone/zeno-filters

Open this address, signed in to GitHub, and press the button under the form:

    https://github.com/zeno-src/packages/issues/new?template=publish.yml&...

The registry checks the package and answers on that page, most often within a few minutes.

zeno publish changes nothing. It checks the package, and what it finds wrong it says, with what to do: a change that is not committed, a tag that is not pushed, a needs line that points at a folder nobody else would have. When everything is in order it gives the address of a form, already filled in. Sending the form is the publishing, and the registry does the rest: it fetches the repository at the tag, checks it again, writes the package’s file and answers.

Three rules keep the registry something that can be relied on.

  • A name is small letters, digits and _, 2 to 40 of them, so that Units and units can never be two packages.

  • The first to publish a name owns it. Its later versions are taken only from the same repository, asked for by the same GitHub account, and you publish only from a repository that is yours.

  • A published version never changes. To change something, publish a new version.

A registry is usually a server that packages are uploaded to, with accounts and tokens of its own. This one needs none of that. It is a repository that zeno reads with git, the accounts are GitHub’s, and nothing is uploaded, because a package is fetched from where it already is. So it costs nothing to keep, and anybody can read all of it. (Decisions 27.3, 27.4, 27.10 and 27.11.)

A registry of your own

Since a registry is any git repository, a company can keep one for packages that are not for the world. A program names it, and every name in that program is then looked up there:

package logger
registry "https://git.example.com/zeno-packages"

needs units at "v1.2.0"

Whoever keeps such a registry adds a package to a clone of it with zeno registry accept, which is the command Zeno’s own registry runs when a form arrives, and then commits and pushes:

$ zeno registry accept . https://git.example.com/units v1.2.0 --owner ada
Accepted units v1.2.0 (9f8e7d6) from https://git.example.com/units
Wrote index/units and index.json

22.6 What can go wrong

Each mistake in a zeno.package is shown with its file and line, as a mistake in a program is. A few of the messages:

error: this does not say which version of `units` is needed. Add `at` and a tag,
a branch or a commit of that repository, as in `needs units from "..." at "v1.0.0"`

error: the package in `lib` is called `filters`, not `filter`. Write `needs filters ...`

error: two packages called `b` are needed: the one in `a/b` and the one in `b`.
A program has one package of each name. Make the `needs` lines agree

And zeno fetch says what the registry has when it does not have what was asked for:

zeno: the registry has no version `v9.0.0` of `units`. It has v1.2.0 and v1.0.0

zeno new starts a program, zeno new --package a package. zeno.package names a package and lists what it needs: a folder with in, a package of the registry by its name and a version with at, or a git repository with from and at. An import whose first word is a needed package reads that package’s folder. zeno fetch gets packages into packages/ and pins them in zeno.lock; running and building never touch the network. zeno search lists the registry, and zeno publish checks a package and says how to ask the registry to take it.

  1. Make a package units_extra with a function that turns a temperature in degC into Fahrenheit as a float, and use it from a program beside it.

  2. Misspell the package’s name in the program’s needs line, and read the message.

  3. Add a test to filters.zeno and run zeno test in the package’s folder (Testing).

  4. Put a package of yours in a git repository, tag it, and need it from a program with from and at.

  5. Give that package an about line and run zeno publish in its folder before the tag is pushed. Read what it says, do what it asks, and run it again.

  6. Make a registry of your own in a folder (git init --bare), take your package into a clone of it with zeno registry accept, and need the package by its name from a program with a registry line.
