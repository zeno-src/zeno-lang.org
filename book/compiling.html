32 Compiling

zeno run reads a program and does what it says, a piece at a time. zeno build turns the same program into C, and the machine’s C compiler turns that into a program of its own: no Zeno needed to run it, and many times faster. The C can also be compiled for a microcontroller, which is where Zeno is going.

32.1 zeno build

primes.zeno

function is_prime(n: int) -> bool {
    if n < 2 {
        return false
    }
    var d = 2
    while d * d <= n {
        if n % d == 0 {
            return false
        }
        d += 1
    }
    return true
}

var count = 0
for n in range(200000) {
    if is_prime(n) {
        count += 1
    }
}
print(count, "primes below 200000")
$ zeno build primes.zeno
Wrote primes.c
Built primes. Run it with ./primes
$ ./primes
17984 primes below 200000

zeno build wrote primes.c, called the C compiler on the machine (cc, which is usually GCC or Clang), and left the program primes beside it. On the computer this book was built on, zeno run takes about two seconds over it, zeno run --vm about one, and ./primes a fiftieth of a second.

32.2 Reading the C

The C file is kept, and it is meant to be read beside the Zeno. Here is is_prime:

$ zeno build primes.zeno > /dev/null
$ grep -A12 "^static bool z_is_prime(int64_t z2_n) {" primes.c
static bool z_is_prime(int64_t z2_n) {
    if (z2_n < 2) {
        return false;
    }
    int64_t z_d = 2;
    while (zeno_mul(z_d, z_d, 6, 11) <= z2_n) {
        if (zeno_mod(z2_n, z_d, 7, 12) == 0) {
            return false;
        }
        z_d = zeno_add(z_d, 1, 10, 9);
    }
    return true;
}

It is the Zeno, line for line. An int is an int64_t. d * d is zeno_mul, which checks for overflow with the compiler’s own built-in and raises an OverflowError with the line and column (the two numbers after the operands) when the answer does not fit. A C compiler that is neither GCC nor Clang has no such built-in, and gets the same check written out in plain C. In front of the program stands Zeno’s runtime, a small C library for text, lists, errors and print, pasted into every file so that the C needs nothing else to compile.

C runs on every processor there is, and every microcontroller vendor ships a C compiler for its chips. Writing C first gave Zeno all of them at once, and C that a person can read is a C that a person can check. (Decisions 5.5 and 5.5b.)

32.3 Build agrees with run

A program must print the same whichever way it is run: zeno run, zeno run --vm, a C build, an LLVM build, a firmware build. Errors included: an uncaught error gives the same message, at the same line and column, in every one. Zeno’s own tests run every test program every way and compare the output byte for byte.

A program that behaves one way under test and another on the board is the worst kind to debug. If zeno run is to be the place where firmware is tried, it must mean exactly what the compiled program means. (Decision 5.5d.)

32.4 A build is strict

zeno build always checks in strict mode: every type must be known, because a compiled program has no tags to carry them (Types, Written and Worked Out). A program that runs with dynamic values under zeno run is told which value is the trouble:

loose.zeno

function same(x) {
    return x
}
print(same(1), same("one"))
$ zeno build loose.zeno
error: strict mode: the parameter `x` of `same` needs a type. It could not be worked out from how it is used
 --> loose.zeno:1:1
  |
1 | function same(x) {
  | ^

1 error found. Nothing was built.

32.5 The options

Option Means
--memory the program reports, as it ends, how much memory it used
--llvm compile to LLVM’s language in place of C, and hand it to clang
--firmware errors travel as values, with no setjmp, as coding standards for firmware ask (Firmware)
--no-collector no garbage collector; every list and object has one owner, and memory comes from a pool of a fixed size (Building with No Collector)
--minimal the least C that runs the program, with no checks (the next section; new in 0.5.2)

lists.zeno

var squares: list[int] = []
for n in range(1000) {
    squares.append(n * n)
}
print(len(squares), squares[999])
$ zeno build --memory lists.zeno
Wrote lists.c
Built lists. Run it with ./lists
$ ./lists
1000 998001
memory: 12 blocks made (16388 bytes), at most 12320 bytes in use at once, 0 collections, 8 blocks freed without the collector

Memory explains the report.

32.6 The least C

The C that zeno build writes keeps every promise Zeno makes, and that takes room. Each sum is checked, each index is checked, each error can say its line, and the whole runtime stands in front of the program in case it is needed: about 4,500 lines of C for a program of one line. Once a program is correct, --minimal writes the other kind of C: the least that runs it, close to what a person would write by hand.

multiples.zeno

function total(limit: int) -> int {
    var sum = 0
    for n in range(limit) {
        if n % 3 == 0 {
            sum += n * 2
        }
    }
    return sum
}

print(f"the total is {total(1000)}")
$ zeno build --minimal multiples.zeno
Wrote multiples.c
Built multiples. Run it with ./multiples
$ ./multiples
the total is 333666
$ grep -c "" multiples.c
44
$ grep -A18 "^static int64_t z_total" multiples.c
static int64_t z_total(int64_t z_limit) {
    int64_t z_sum = 0;
    int64_t t1 = z_limit;
    for (int64_t z_n = 0; z_n < t1; z_n++) {
        if (zeno_mod(z_n, 3) == 0) {
            z_sum += z_n * 2;
        }
    }
    return z_sum;
}

int main(void) {
    printf("the total is %lld\n", (long long)z_total(1000));
    return 0;
}

The number after the answer is how many lines the C file has, and the rest is the program, whole. n * 2 is C’s own *, with nothing checking it. print is printf. No call ends in a line and a column. Of the runtime, one function is left, a few lines above z_total in the file: zeno_mod, because -7 % 3 is 2 in Zeno and  − 1 in C, and that is not a check but what % means.

What is given up is every check. In a minimal build a mistake does what it would do in C:

zeno build zeno build --minimal
an index out of range IndexError reads or writes whatever memory is there
a key the dict does not have KeyError reads an item that is not there
a whole number that overflows OverflowError no defined result
a whole number divided by zero ZeroDivisionError what the processor does; on a computer the program is stopped
a float divided by zero ZeroDivisionError infinity, or NaN
u8(300) ValueError 300 goes on as it is
an error nothing catches says what, and the line says what

What is kept is everything a correct program can meet. int("ten") still raises a ValueError and a file that is not there a FileError, try and except work as they did, and the program prints what it printed before, to the last digit of a float.

--minimal goes with --firmware, --owned and --no-collector. A program that makes a list still needs something to free it, and the garbage collector is some 500 lines of C that no option makes small, so the smallest C for such a program comes from --minimal --no-collector. The file gets much smaller, 23 lines for a program that prints one line; the program the C compiler makes of it gets a little smaller, since the C compiler never put an unused function into it in the first place.

Two readers want two things from the C. While a program is being written, the C should stop at the first mistake and say where. When it is done and its C is to be read, reviewed or carried into another project, every line that is not the program is in the way. So there are two builds, and the one that checks is the one you get without asking. (Decisions 30.1 to 30.12; docs/minimal.md has the whole table and the sizes.)

32.7 Through LLVM

zeno build --llvm writes the program in LLVM’s intermediate language, the one Clang, Rust and Swift compile through, and hands it to clang. The program is the same, and prints the same:

$ zeno build --llvm primes.zeno
Wrote primes.ll and primes_runtime.c
Built primes. Run it with ./primes
$ ./primes
17984 primes below 200000

The IR is written as text by Zeno itself, with no LLVM library, and primes.ll can be read like primes.c. LLVM brings its own optimiser and every processor it knows. Inside Zeno shows a piece of it.

32.8 For another processor

zeno build compiles for the computer it runs on. A microcontroller has a C compiler of its own, flags that say which processor it is, a file that runs before main, and a linker script that says where its flash and RAM are. Those four are the same for every program on one board, so they are written down once, in a folder, and --board names the folder:

$ zeno build --board boards/qemu-cortex-m3 blink.zeno
Wrote blink.c
Built blink.elf for the board in `boards/qemu-cortex-m3`.
Run it with: qemu-system-arm -M lm3s6965evb -nographic -kernel blink.elf

The folder has a file called zeno.board, read as a zeno.package is. Each word in quotes is one word of the command the compiler is given:

about "An ARM Cortex-M3 that QEMU emulates"

compiler "arm-none-eabi-gcc"
flags "-mcpu=cortex-m3" "-mthumb"
sources "startup.c" "system.c"
script "link.ld"
link "-nostartfiles" "-Wl,--gc-sections"
run "qemu-system-arm" "-M" "lm3s6965evb" "-nographic" "-kernel"

(The board’s real run line has one more word, "-semihosting", which lets the program tell QEMU that it has ended.)

compiler is the one line a board must have. header names the header with the board’s own functions (Firmware); a board without one, like this one, has the simulated pins. zeno build shows the run command and does not run it: on a real board it writes to the chip.

The program is built as --no-collector builds it, because the garbage collector takes its memory 64 KB at a time and this chip has 64 KB in all. --minimal, --release, --fast and --memory go with --board.

The board in the example comes with Zeno, in its repository, and needs no hardware: QEMU emulates an ARM Cortex-M3 with 256 KB of flash and 64 KB of RAM. Every example in this book that a build with no collector accepts is built for it and compared with the same program on a computer, each time the compiler changes. No program of Zeno’s has run on a real board yet.

Beside it is a second folder for the same chip, boards/lm3s6965evb, which has a header line. There a pin is a bit of one of the chip’s ports and not a line of text, and print goes out of the chip’s serial port through four functions of the header (The Board), with no printf and no exit under the program:

$ zeno build --board boards/qemu-cortex-m3 hello.zeno
$ arm-none-eabi-size hello.elf
   text    data     bss     dec     hex filename
   8096    1376     380    9852    267c hello.elf
$ zeno build --board boards/lm3s6965evb hello.zeno
$ arm-none-eabi-size hello.elf
   text    data     bss     dec     hex filename
    920      16       4     940     3ac hello.elf

A number with a fraction is made into text by Zeno’s own runtime on both boards, with whole numbers. The C library’s snprintf would be 28 KB of this chip’s flash, and the runtime’s digits are 1 to 4.

Building C for a target is a job the target’s own tools already do well, with the flags, linker scripts and start-up code that only they know. So Zeno copies none of them. A board’s folder names the tools an engineer already has, and Zeno types the one long command that was typed by hand before. The flags are in a folder of the board’s and not in the program’s package, because one program is built for two boards and one board runs many programs. (Decisions 5.12c and 51; new in 0.7.)

32.9 What does not compile yet

Nearly the whole language compiles. A few corners do not, and zeno build names each one and points at the line, while zeno run still runs the program:

named.zeno

function area(width: int, height: int) -> int {
    return width * height
}
let measure = area
print(measure(height = 2, width = 3))
$ zeno build named.zeno
error: `zeno build` cannot compile named arguments to a function held in a variable yet. `zeno run` can still run this program
 --> named.zeno:5:7
  |
5 | print(measure(height = 2, width = 3))
  |       ^

The type of a function value has no names for its parameters, so a build cannot know which argument is which; zeno run reads them off the function the variable holds. Passing them in order builds. The table in docs/compiler.md lists every such corner with its reason, and a test holds the compilers to it. Since 0.8.0 a function with a name written inside another, a default worked out at the call, a method used as a value and a function value that raises all build; Appendix G has what is left.

A program that uses the library of another language through import python or one of its like is refused too, because a built program must run where that language may not be (Libraries of Other Languages). A library of C is the other way round: a build calls it directly and links it in, on a board as well (Libraries of C).

32.10 In another language (new in 0.5)

zeno build --target writes the program in another language: a file you can read, keep, and run with that language’s own tools. The languages are js (JavaScript, for Node), ts (TypeScript), html (a page that runs the program), py (Python), php, go, java, cs (C#), cpp (C++), rust, and wasm (WebAssembly, built through Rust). Zeno 0.5.2 added four: lua, ruby, dart and kotlin.

area.zeno

import math

function area(r: float) -> float {
    return math.pi * r * r
}
print(area(2.0))
$ zeno build --target js area.zeno
Wrote area.js. Run it with `node area.js`
$ node area.js
12.566370614359172
$ zeno build --target py area.zeno
Wrote area.py. Run it with `python3 area.py`
$ python3 area.py
12.566370614359172

The file is written by fixed rules, so the same program always gives the same file, letter for letter. Each language gets a runtime of its own, at the top of the file, which does what zeno run does, step for step: an int still overflows in JavaScript, whose numbers never do, and in Python, whose whole numbers never stop growing.

$ zeno build --target py area.zeno > /dev/null
$ grep -A6 "^def main" area.py
def main():
    area = None
    math_ = Z.Cell()
    def z_f1(r, *, math_=math_):
        return Z.mul(Z.mul(Z.builtin("math.pi"), r, 4), r, 4)
    area = Z.fn("area", ["r"], [False], z_f1)
    math_.v = Z.module("math")

Z.mul(a, b, 4) multiplies as Zeno multiplies, and stops with Zeno’s message for line 4 if the answer does not fit. math is math_ because math is a name the languages’ own libraries use.

As with zeno build itself, a tool holds every target to zeno run: tools/targets.py runs every example and every sample of this book in every language and compares what each prints, and it runs once a week on the newest version of each language.

A program that uses the board, unsafe or manual memory is refused: those belong to a program compiled to machine code. The page cannot use the keyboard or files, or sleep.

A program you have written in Zeno can then live where another language lives: on a web page, in a Python project, on a Java server. And it is a way to learn: the same program, written by fixed rules in fifteen languages, shows what each language needs said that Zeno does not. (Decisions 24.1 to 24.34; docs/targets.md has every target.)

zeno build writes C, compiles it with the machine’s compiler, and keeps both. The compiled program prints what zeno run prints, errors included, and is many times faster. A build is always strict. --llvm goes through LLVM; --memory, --firmware and --no-collector are for the board. For another processor, the C goes to that processor’s compiler. --minimal writes the least C for a program that is already correct, with no checks in it. --target writes the program in another language instead.

  1. Build a program from an earlier chapter, open its C file, and find each of your functions in it.

  2. Time zeno run, zeno run --vm and the built program on the primes example, with a larger limit.

  3. Make a program overflow an int and build it. Is the message the same as zeno run’s?

  4. Build with --llvm, open the .ll file, and find is_prime.

  5. Build the primes example with --minimal and read the whole of primes.c. Then read a list past its end in a small program, and build that both ways.

  6. Build the area example with --target go and --target java. Find area in each, and compare the two with the Python.
