25 Another Language in a Zeno File

Some code is already written, and is in another language: a checksum out of a board’s firmware, a few lines of Python that use a library, a function of JavaScript from a page. Since 0.9 an inline block holds it in a .zeno file as it was written, and the program calls it:

ones.zeno

import c

let bits = inline c {
    #include <stdint.h>

    /* How many bits of x are 1. */
    int ones(uint32_t x) {
        int count = 0;
        for (; x != 0; x &= x - 1) {
            count++;
        }
        return count;
    }
}

print(bits.ones(0xA5))
4

What is between the first line and the last } is C, and is not read as Zeno. bits is a library of C, as c.library gives one (Libraries of C), and ones is a function of it.

There are three kinds of block:

Written Holds Gives
inline c C a library of C: the functions the block writes out
inline python Python a module of Python: what the block defines
inline node JavaScript what the block puts in exports

Nothing changes for a program that has no block. A block is asked for twice: by the word inline, and by the import of its language at the top of the file. inline is not a reserved word, and let inline = 3 still means what it meant.

25.1 Why Zeno is not a superset of C, or of Python

It would be one way to use code that is already written: make every program of C a program of Zeno, as every program of C is nearly one of C++, and every program of JavaScript is one of TypeScript. Zeno does not, for three reasons.

A superset has to take every program of the other language, for ever, with every mistake that language allows. The first thing given up would be the checks Zeno is for: a sum that cannot overflow unseen, a name that cannot be none unseen. A superset of two languages cannot exist where they disagree, and a / b, {} and 'x' each mean something else in C, Python and JavaScript. And a superset of one language is a dialect of it: TypeScript cannot mend the == of JavaScript.

A block gets the same result for the person with the code. It is used as it is, today, by that language’s own compiler, and Zeno stays one language with one set of rules.

25.2 What it needs

What the import of the language needs, and nothing more: a C compiler for inline c, as for import c and zeno build; Python 3 for inline python; Node for inline node (Libraries of Other Languages).

25.3 Writing a block

let name = inline c {
    ...the other language...
}

  • A block is the whole value of a let. What it has is then used through that name. It may be at the top of a file, in a function, or in a test.

  • The first line ends with the {. inline, the language, {, and the end of the line.

  • Everything inside is further in than the line that opens the block. How far is up to you; zeno format sets it one step in.

  • The block ends at a line that holds only }, as far in as the line that opened it.

That last rule is why a block needs no care. A } of C is always further in than the block’s own, so it ends nothing. Zeno does not look for the other language’s strings and comments, and so cannot mistake one:

odd.zeno

import c

let odd = inline c {
    /* A } in a comment, */
    const char *closing(void) { return "} and one in a text"; }
}

print(odd.closing())
} and one in a text

The indentation that every line of a block shares is not part of the block. Each line keeps how far in it is from the others, which in Python is part of the program.

To find the end of a block by counting braces, Zeno would have to know what a brace inside a string or a comment looks like in each language: "}", '}', /* } */, a template of JavaScript, a regular expression, a raw string of Python. That is a small reader for each language, each wrong somewhere, and the mistake it would make is the worst kind: the block ends early, and the rest of the other language’s code is read as Zeno. A line that holds only } at the first line’s own indentation is found with no knowledge of the other language, and can be seen with the eye. It is the one place in Zeno where indentation means something, and a line that breaks the rule is refused, never guessed at. (Decision 61.3.)

25.4 A block of C

Each function that is written out in the block, with its body, and is not static, is a function of the library. Its types are read from its own first line, so nothing is declared a second time:

frame.zeno

import c

let frame = inline c {
    #include <stdint.h>
    #include <stddef.h>

    #define POLYNOMIAL 0xA001

    static uint16_t step(uint16_t crc) {
        return (crc & 1) ? (crc >> 1) ^ POLYNOMIAL : crc >> 1;
    }

    uint16_t crc16(const uint8_t *data, size_t length) {
        uint16_t crc = 0xFFFF;
        for (size_t i = 0; i < length; i++) {
            crc ^= data[i];
            for (int bit = 0; bit < 8; bit++) {
                crc = step(crc);
            }
        }
        return crc;
    }
}

let request: list[u8] = [0x01, 0x03, 0x00, 0x6B, 0x00, 0x03]
print(frame.crc16(request, len(request)))
6004

crc16 is a function of frame. step is static, so it is the block’s own, and so are POLYNOMIAL, a variable, a typedef and a struct: they are there for the block’s functions, and Zeno leaves them alone.

A call is checked before the program runs, as a call of a function of Zeno is:

calls.zeno

import c

let frame = inline c {
    #include <stdint.h>
    #include <stddef.h>

    static uint16_t step(uint16_t crc) { return crc >> 1; }

    uint16_t crc16(const uint8_t *data, size_t length) {
        uint16_t crc = 0xFFFF;
        for (size_t i = 0; i < length; i++) {
            crc = step(crc ^ data[i]);
        }
        return crc;
    }
}

print(frame.crc16(3, 1))
print(frame.crc16([1, 2]))
print(frame.step(1))

Values go across as they do for c.library: a whole number is checked to fit the type the function takes, a list is lent for a pointer and copied back unless the pointer is to const, text goes as a const char *, and any other pointer C gives back is kept as it is. It is one table for both, and it is in the last chapter. A header is included as in C: one of the system in < >, one of the program in " ", found from the folder of the .zeno file.

A mistake in the block is the C compiler’s to find, and it is told where each line of the block was written, so what it says names the .zeno file:

sensor.zeno

import c

let lib = inline c {
    int twice(int x) { return 2 * y; }
}

print(lib.twice(21))

The line is the line of the .zeno file. The column is counted from where the lines of the block begin, since the indentation they share is not part of the block.

A block that does not compile stops the program where the block is. No try catches it: the program is wrong, and running it again will not help.

A block of C cannot have What to do
a function Zeno cannot call that is not static: one that takes ..., a function, or a whole struct mark it static if only the block calls it, or write a function beside it that Zeno can call
no function Zeno can call write one out, with its body, without static
C++ functions of C++ marked extern "C", built into a library, go to c.library

25.5 What zeno build does with a block

A build that writes C writes the block into the program’s C, as it was written. There is no library beside the program and nothing between a call and the function: frame.crc16(...) is a call of crc16 in the same file, which the C compiler may put in line.

$ zeno build frame.zeno
Wrote frame.c
Built frame. Run it with ./frame
$ ./frame
6004
$ zeno build --no-collector --minimal frame.zeno
Wrote frame.c
Built frame. Run it with ./frame
$ ./frame
6004
$ grep -c "^#line" frame.c
2

Every build that writes C does it: a plain one, --firmware, --no-collector, --owned, --minimal, --release, --fast, --board, and zeno test --build (Compiling). The last line above counts the lines of the built C that begin with #line. There are two: one before the block, which names the .zeno file and the line the block began on, and one after it, which gives the lines that follow back to the C file. So a mistake the C compiler finds, and a line a debugger stops at, is a line of the .zeno file.

Under zeno run the block is built once into a small library, kept, and called through the helper that import c uses; it is built again when the block changes.

25.6 Assembly

Assembly is written inside a block of C, as the C compiler takes it:

import c

let cpu = inline c {
    #include <stdint.h>

    /* Interrupts off, on a Cortex-M. What PRIMASK was is given back. */
    uint32_t interrupts_off(void) {
        uint32_t was;
        __asm__ volatile ("mrs %0, primask\n cpsid i" : "=r" (was));
        return was;
    }
}

There is no inline asm. Assembly has no types, so nothing in it says what a routine takes or gives, and the C function around it is what says so. It is also not one language: each processor has its own instructions and each compiler its own way of writing them, and the C compiler already knows both.

A whole file of assembly is given to c.library, beside the .c files it takes:

let start = c.library("startup.s", "void reset(void);")

The C compiler assembles it, a .s as it is and a .S after reading its #include and #define lines.

25.7 A block of Python

stats.zeno

import python

let stats = inline python {
    import statistics

    def summary(readings):
        """The middle and the spread of some readings."""
        return [statistics.median(readings), statistics.pstdev(readings)]
}

print(stats.summary([21.5, 22.0, 23.5]))
[22.0, 0.8498365855987975]

The block is a module of Python: what python.module would give if the lines were in a .py file. Everything it defines is reached with a dot: a function, a class, a variable, and a module the block imported (stats.statistics). Values go across as for import python.

The block runs when the program gets to it, once, top to bottom, as a module does when it is imported. An error of Python in it stops the program, and names the line of the .zeno file:

wrong.zeno

import python

let stats = inline python {
    def summary(readings:
        return max(readings)
}

print(stats.summary([1, 2]))
error: this `inline python` block could not be started. Python said: SyntaxError: '(' was never closed (wrong.zeno, line 4)
 --> wrong.zeno:3:13
  |
3 | let stats = inline python {
  |             ^

25.8 A block of JavaScript

written.zeno

import node

let written = inline node {
    exports.number = (value, place) => new Intl.NumberFormat(place).format(value)
}

print(written.number(1234567.5, "en-IN"))
print(written.number(1234567.5, "de-DE"))
12,34,567.5
1.234.567,5

The block is a module of Node, as a .js file is: what it puts in exports, or gives module.exports, is what the block gives, and require finds the packages npm install put in the program’s folder. It is a module of the older kind, with require and exports; import and export are not read there. Values go across as for import node.

25.9 What each command does with a block

inline c inline python, inline node
zeno run, zeno test built once, kept, and called through the C helper given to the Python or the Node that the import starts
zeno check the functions and every call of them are checked checked when the program runs
zeno build, and every build that writes C written into the program’s C refused
zeno check --strict as zeno check refused: what it gives is not known before the program runs
zeno build --llvm refused refused
zeno build --target refused refused
the playground refused: a page has no C compiler refused
zeno format the lines of the block are left as they are, one step in the same

A refusal is an error with the line of the block, when the program is checked or built. A block is never skipped.

25.10 What Zeno cannot check

The code in a block is the other language’s, and Zeno checks none of it. A pointer that is wrong in a block of C damages memory as it does in C: a built program stops or goes wrong, and under zeno run the helper stops and Zeno says which call it was waiting for. The blocks of a program are the lines to read then, and grep -n "inline c" finds them all, as grep -n unsafe finds the other lines of that kind (Unsafe Code).

25.11 What is not there yet

  • A library for a block. A block of C that needs a library other than C’s own (-lz) has nowhere to say so. Until it has, the code goes in a .c file given to c.library with the library.

  • A constant of a block. A #define or a variable of a block is not seen by Zeno; a function that gives it is. c.library can declare a value.

  • Small types given back as themselves. A uint16_t comes back as an int, as for c.library.

  • Blocks of Ruby, PHP, Lua and C#. Each has an import already and can be given a block in the same way.

  • zeno build –llvm with a block of C.

25.12 How it is built

The lexer decides: inline, a name, a { and the end of the line begin a block, and it is the one place the lexer looks further than two characters ahead. It reads the lines to the closing one and makes of them one token, which holds the language and the text. The parser allows that token only as the value of a let.

For a block of C, the checker finds the functions: it goes through the text once, stepping over comments, strings, lines that begin with # and bodies between braces, and keeps the first line of each function that is not static. Those lines are what c.library would have been given, and from there a block is a library: the checker, zeno run and zeno build use what import c built. A block of Python is compiled by Python’s own compile, with as many empty lines before it as the .zeno file has above it, so that the line numbers Python counts are the file’s. The reasons are chapter 61 of docs/decisions.md, and examples/bits.zeno and examples/report.zeno are two whole programs.

25.13 Things to try

  1. Run examples/bits.zeno, then build it and run what was built. Open bits.c and find the block. What is on the line before it, and on the line after?

  2. In the first program of this chapter, write count+++; in the block and run it. Which file and line does the C compiler name?

  3. Mark ones as static and run zeno check. Read the message. Then write a second function that is not static and calls it.

  4. Write let m = inline python { in a file with no import python, and read what Zeno says.

  5. Write a block of Python with a class in it, make an object of the class from Zeno, and call a method. Then do the same with a class of JavaScript and node.new.

  6. Put a } on a line by itself in the middle of a block of C, as far in as the rest of the block. Does it end the block? Move it out to where the let begins and run zeno check again.
