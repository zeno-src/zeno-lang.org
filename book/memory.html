34 Memory

Numbers and bools live in the variables that hold them, and need no memory of their own. Text that is built, lists, objects, enum values that carry something, and functions that keep variables all need memory while the program runs, and somebody must give it back when the program is done with it. This chapter is about how an ordinary compiled Zeno program does that, with a garbage collector. The next three chapters are about the ways firmware can do without one.

zeno run needs none of this: the interpreter is a Rust program, and Rust frees its values for it. Everything here is about zeno build.

34.1 What takes memory

  • text that is built: a + b, an f string, text.upper();

  • every list, and every dict;

  • every object, and every enum value that carries something;

  • a function written inside another, with the variables it keeps.

Each of these is a block: a piece of memory from the C library’s malloc. The question is when to give each block back with free.

34.2 The question nobody can answer in advance

function label(reading: Reading) -> str {
    let text = f"tick {reading.tick}"
    return text
}

Is text finished with when label returns? No: the caller has it now, and may put it in a list, which goes into an object, which a function remembers. In C the programmer keeps track of all that by hand, and the mistakes are famous: freeing too early, so that the program uses memory that is now something else; freeing twice; or never freeing at all.

A collector answers a simpler question, while the program runs: can the program still reach this block? If no variable leads to it, directly or through other blocks, nothing can ever use it again, and it is safe to free.

34.3 Mark and sweep

Zeno’s collector is the oldest and simplest kind. It was invented for Lisp in 1960, and it is what MicroPython runs on microcontrollers.

  1. Every block is handed out from a page: 64 KB of memory holding blocks of one size, which keeps a bit for each block to say whether it is in use.

  2. Mark. Start from the variables, the roots. Whatever a root points at is in use: mark it. Whatever a marked block points at is in use too. Carry on until nothing new turns up.

  3. Sweep. Go through the pages. A block in use with no mark cannot be reached: free it.

Two objects that point at each other, and at nothing in use, are freed like anything else: no root reaches them, so neither is marked. That is the case that defeats the other common method, counting references.

The roots are the variables at the top of the file, which the compiler lists, and everything on the C stack: the collector reads the stack from the function running now back to main, a word at a time, and asks of each word whether it is the address of one of its blocks. When unsure, it keeps, so it can never free a block in use. The question is quick to answer: every page starts at an address that is a multiple of 64 KB, and a hash table says which page covers each 64 KB of memory, so one look and one division find the block a word points into. (Until version 0.3 the collector kept one table of every block, sorted it at each collection, and searched it for every word; on a program with millions of blocks, the pages made it five times faster. Decision 22.5.)

A word that points just past the end of a block is also the start of the next one. Only the rows that hold a list’s items, which a loop may walk off the end of, count such a word for the block before; they have pages of their own for that reason. When every block counted it, each block kept its neighbour alive, and the neighbour its own: a benchmark that needed 130 MB held 2.3 GB. (Decision 22.10.)

34.4 Young and old

Most blocks are garbage soon after they are made, and a block that has lived through one collection usually lives through many. So most collections are small: they look only at the blocks made since the last one, the young, and take every block that lived through a collection, the old, to be still in use. A block is old when its mark is still there from the collection it lived through; a small collection stops at it instead of looking inside it again. Once the old have grown to twice what the last full collection kept, the next collection is full and looks at everything.

There is one danger: an old block given a pointer to a young one since the last collection. Nobody would look inside the old block, and the young one would be freed while in use. So after each collection, every full page of blocks that can hold pointers is made read-only with the system’s mprotect. The first write to such a page stops the program for a moment; a handler opens the page again and notes that it was written, and the next small collection looks inside its old blocks. The processor keeps watch, so no line of the compiled program has to. On a program that keeps a tree of two million nodes for its whole run, this took the time from 11 seconds to 7. On a chip, and for now on Windows, every collection is full. (Decisions 22.10 and 22.14.)

34.5 Seeing it work

zeno build --memory makes a program that reports, as it ends, what memory it used. This one, from the examples folder, logs a reading every tick for 50 000 ticks, and keeps only the last few and the hottest:

memory.zeno

# memory.zeno: a program that makes far more than it keeps.
#
#     zeno run examples/memory.zeno              run it with the interpreter
#     zeno build --memory examples/memory.zeno   compile it, with a memory report
#     ./memory
#
# A logger takes a reading every tick. Each reading is an object with some
# text in it, so every tick takes a little memory. Only the last few
# readings and the hottest one are kept. The rest is garbage, and the
# garbage collector in the compiled program gives that memory back.

class Reading {
    tick: int
    celsius: float
    note: str
}

function describe(reading: Reading) -> str {
    return f"tick {reading.tick}: {reading.celsius:.1f} C ({reading.note})"
}

var recent: list[Reading] = []          # the last few readings
var hottest: Reading or none = none
var lines = 0

for tick in range(50000) {
    let celsius = 20.0 + (tick * 37 % 151) / 10.0
    let reading = Reading(tick, celsius, f"sample {tick}")

    # Start a new list every five readings. The old list, and the readings
    # only it knew about, can no longer be reached from any variable.
    if len(recent) == 5 {
        recent = []
    }
    recent.append(reading)

    if hottest is none or reading.celsius > hottest.celsius {
        hottest = reading
    }

    # Text that is made, measured and forgotten at once.
    lines += len(describe(reading).split())
}

print("words logged:", lines)
print("still held:")
for reading in recent {
    print("  " + describe(reading))
}
if hottest is not none {
    print("hottest: " + describe(hottest))
}

# Built with --memory, the program ends with a line like this one:
#
#   memory: 780027 blocks made (13222784 bytes), at most 1048576 bytes in use at once, 12 collections
#
# Thirteen megabytes were asked for. One megabyte at a time was enough.
$ zeno build --memory memory.zeno > /dev/null
$ ./memory
words logged: 300000
still held:
  tick 49995: 26.5 C (sample 49995)
  tick 49996: 30.2 C (sample 49996)
  tick 49997: 33.9 C (sample 49997)
  tick 49998: 22.5 C (sample 49998)
  tick 49999: 26.2 C (sample 49999)
hottest: tick 102: 35.0 C (sample 102)
memory: 730027 blocks made (13222796 bytes), at most 4194304 bytes in use at once, 4 collections, 60002 blocks freed without the collector

The last line is the report. The program asked for thirteen megabytes, a few bytes at a time, and never held more than one megabyte or so at once, because the collector ran when it was needed and gave the rest back. The last number counts blocks freed at a line the compiler could point to, without waiting for the collector: the old storage of a list that has just grown, and the copy that a for loop walks.

34.6 When it runs

Collecting takes time, in proportion to what it looks at, so it is not done on every allocation. The runtime counts the bytes in use and collects when they pass a limit; after each collection the limit becomes twice what survived. A program that keeps little is collected often and cheaply, and one that keeps a lot is left alone for longer. And if malloc itself says there is no more memory, the collector runs and the request is tried again. On a board with 64 KB of memory, that second trigger is the one that matters.

34.7 What it costs

  • Pauses. While the collector runs, the program does not. A small collection’s pause grows with what was made since the last one, a full one’s with all the memory in use. A control loop that must answer within microseconds should not make blocks inside the loop. Numbers, bools and fixed text never do.

  • A little memory for each block: two bits in its page, and the room left over when a block is rounded up to its page’s size.

  • It leans on the C compiler. Reading the stack word by word is not something the C standard describes. Every mainstream compiler and processor allows it, and the Boehm collector, Ruby and MicroPython have relied on it for decades.

Sharing, with a collector to make it safe, is what Python, Java and JavaScript programmers expect, and it lets a program be written without thinking about memory at all. Counting references cannot free a cycle and costs on every assignment. Rust’s ownership everywhere would make every Zeno program pay the hardest part of Rust. So the collector is the default, and the next chapters give firmware the other choices where it needs them. (Decision 5.7.)

34.8 Three ways to manage memory

Build Memory
zeno build shared values and a collector: this chapter
owned values one owner, freed where its block ends, in any build: Ownership
memory owned every list and object has one owner, and there is no collector: Rust’s way. Said once, in zeno.package, or with zeno build --owned. Memory grows as the program needs it
--no-collector the same rules for a chip: memory comes from a fixed pool. Building with No Collector

A program chooses with one line in its zeno.package:

package server
memory owned

and zeno build, zeno check and zeno run all follow it. memory collector is what a program gets when nothing is said. It is a choice for the whole program because how memory is freed has to go with each value, and a value is used on many lines; a single value can still be owned in a collector program. (Decision 22.1.)

One file of a program can choose too. A file that begins with the line memory owned makes every class it declares an owned class, as if each were written owned class: its objects have one owner and are freed where that owner ends, even in a program with a collector, while the rest of the program shares its values as before. Where the two meet, the rules are those of owned values in a collector program: a function that only looks can be given any object, and an object with one owner cannot be kept in a shared list. When every file says memory owned, the whole program is owned and built with no collector. (Decision 22.9.)

--release goes with any of them: whole numbers wrap round on overflow, as the processor does, instead of stopping the program, and every other check stays. It is what Rust’s release builds do. On the benchmarks in the repository’s bench folder, an owned release build of a program that makes millions of small objects runs as fast as the same program in C, or faster, and the collector build about two times slower. (Decision 22.3.)

--fast goes further. It leaves out every check that a correct program never fails, as C leaves them out: a list index out of range reads whatever memory is there, a float divided by zero is infinity, and the square root of a number below zero is NaN. A whole number divided by zero is still caught, because C would stop the program with a signal or worse. The C compiler is asked to try harder too (-O3).

Overflow is where --fast and --release part. With --release a sum that overflows wraps round: a wrong number, but a known one. With --fast it has no defined result, as in C, and the C compiler builds on its not happening: a count that starts at 0 and only goes up is never below zero, so the % of it needs no care for numbers below zero. That one piece of knowledge is what makes a tight loop of whole numbers the very same instructions a C program gets. A program that does overflow may print a wrong number or never leave a loop. Since an overflow is an error in Zeno, a program that runs clean under zeno run has none.

Use --fast for a program whose tests pass, when every last bit of speed matters; build it the ordinary way while it is being written. (Decisions 23.1 and 23.6.)

--minimal is about the C and not about speed. It leaves out every check, the ones --fast keeps too, and every part of the runtime the program does not use, so that the C file is short enough to read whole (Compiling).

Memory a program asks for itself with allocate is apart from all of these: the collector never looks at it, and the program gives it back with free (Unsafe Code).

Built text, lists, dicts, objects, enum values that carry something and functions that keep variables take memory. A compiled program frees it with a mark-and-sweep collector, which frees whatever no variable can reach, cycles included. It runs when memory in use passes a limit, or when malloc runs out. --memory reports what a program used. The cost is pauses, a little memory per block, and a habit of C compilers that every one of them keeps.

  1. Build memory.zeno with --memory and change the number of ticks. Which numbers in the report grow, and which do not?

  2. Write a loop that builds a text with + a thousand times, and build it with --memory. Then build the same text once with join. Compare the reports.

  3. Make two objects that point at each other through fields that may be none, drop every variable that leads to them in a loop, and check that the memory in use stays low.
