30 Testing

A test is a small program that checks a part of a bigger one, and says clearly when the part is wrong. Firmware that has been tested on a computer before it reaches a board is firmware that wastes fewer afternoons at the bench. Zeno has tests in the language: a test block, an assert statement, and the command zeno test.

30.1 A first test

temperature.zeno

function to_fahrenheit(celsius: float) -> float {
    return celsius * 1.8 + 32.0
}

test "water freezes at 32" {
    assert to_fahrenheit(0.0) == 32.0
}

test "water boils at 212" {
    assert to_fahrenheit(100.0) == 212.0
}
$ zeno test temperature.zeno
temperature.zeno
  ok      water freezes at 32
  ok      water boils at 212

2 tests: 2 passed, 0 failed.

A test is the word test, a name in quotes that says in ordinary words what it checks, and a block. It stands at the top of a file, beside what it tests. zeno test runs the file as zeno run would, and then each test, in the order written.

To run only some of the tests, give --only some of the words of their names. The file still runs first, since the tests may use what it made:

$ zeno test --only boils temperature.zeno
temperature.zeno
  ok      water boils at 212

1 test: 1 passed, 0 failed.

zeno run goes past the tests, and zeno build leaves them out altogether, so a board pays nothing for them. But they are checked with the program by zeno check and zeno run, so a test cannot go stale without anybody noticing.

30.2 assert

assert and a condition say what must be so. When the condition is a comparison, a failure shows what was on each side:

average.zeno

function average(values: list[float]) -> float {
    return sum(values) / float(len(values) + 1)
}

test "the average of one number is that number" {
    assert average([4.0]) == 4.0
}

test "an average lies between the smallest and the largest" {
    let values = [1.0, 2.0, 6.0]
    assert min(values) <= average(values)
}
$ zeno test average.zeno
average.zeno
  FAILED  the average of one number is that number
  ok      an average lies between the smallest and the largest

FAILED: the average of one number is that number
error: this is false. The left of `==` is 2.0, and the right is 4.0
 --> average.zeno:6:12
  |
6 |     assert average([4.0]) == 4.0
  |            ^


2 tests: 1 passed, 1 failed.

The first test failed, and the message shows that the left side was 2.0 where 4.0 was wanted: the + 1 is the bug. The second test passed, because a wrong average can still lie in the right range. A failed assert ends its test; the next test runs anyway. The command fails when any test fails, so a script or a build server can tell.

Other languages grow a family of asserts, assert_eq, assert_ne, assertIn, each so that a failure can show the values. Zeno has the comparison in front of it, so the one assert can show them, and there is one thing to learn. (Decision 10.17.)

assert is only for tests. In a program, if and raise say what is wrong and to whom, and can be caught. A failed assert is not an error of the program, so except Error does not catch it.

30.3 A message for a failure

When the two sides of a comparison do not say why they matter, an assert can say it, after a comma:

smooth.zeno

function smooth(readings: list[float]) -> list[float] {
    var result: list[float] = []
    for index in range(1, len(readings)) {
        result.append((readings[index - 1] + readings[index]) / 2.0)
    }
    return result
}

test "smoothing gives one value for each reading" {
    let readings = [20.0, 22.0, 21.0]
    let smoothed = smooth(readings)
    assert len(smoothed) == len(readings), f"the readings gave {smoothed}"
}
$ zeno test smooth.zeno
smooth.zeno
  FAILED  smoothing gives one value for each reading

FAILED: smoothing gives one value for each reading
error: the readings gave [21.0, 21.5]
this is false. The left of `==` is 2, and the right is 3
  --> smooth.zeno:12:12
   |
12 |     assert len(smoothed) == len(readings), f"the readings gave {smoothed}"
   |            ^


1 test: 0 passed, 1 failed.

The text is printed on a line of its own, above the line that says what was false, which stays. Here the sides say only that 2 is not 3; the text shows the list that came back, and that the first reading has no value of its own. A condition that is not a comparison, such as assert heater.is_on(), shows no values at all, and there the text is the only way to say more than “this is false”.

What comes after the comma must be text, and only one text: when total is an int, assert total == 6, total is refused, and f"the total was {total}" is what to write. An f-string makes anything text, so nothing is lost. The text is worked out only when the assert fails, so a passing test does not pay for it, and it can use what is only there when something has gone wrong. assert raises takes no text: its failure already says what was wanted and what came.

The test’s name and the two sides of a comparison say most of what a message would say, which is why the first versions of Zeno had none. What they cannot say is why the values matter, in the words of the thing being tested, and a condition with no comparison in it says nothing but that it is false. The comma is how Python writes it, so most readers have seen it, and after the one expression of an assert it can mean nothing else. assert c else "text" would make else begin a value, and assert(c, "text") would read as a call. (Decision 60.1.)

30.4 Testing that something fails

Fault paths are half of what firmware has to get right. assert raises checks that a block raises an error of a kind:

speed.zeno

function check_speed(speed: int) -> int raises ValueError {
    if speed < 0 or speed > 100 {
        raise ValueError(f"a speed is 0 to 100, and {speed} is not")
    }
    return speed
}

test "speeds in range are kept" {
    assert check_speed(0) == 0
    assert check_speed(100) == 100
}

test "speeds out of range are refused" {
    assert raises ValueError {
        check_speed(101)
    }
    assert raises ValueError {
        check_speed(-1)
    }
}
$ zeno test speed.zeno
speed.zeno
  ok      speeds in range are kept
  ok      speeds out of range are refused

2 tests: 2 passed, 0 failed.

The test fails if the block raises nothing, or raises another kind, and says which. To take an error of any kind, name Error: assert raises Error.

30.5 Where tests go

A test can stand in the file it tests, and then it sees what is private to that file, which is usually where the things worth testing are. A file of tests alone, such as ring_test.zeno importing ring, is the same thing with nothing else in it.

zeno test with a folder tests every file in it, and below it, that has a test. With no folder it means the folder it is run in:

$ zeno test ring
ring/ring.zeno
  ok      a new ring is empty
  ok      bytes come out in the order they went in
  ok      a full ring keeps what it has
  ok      the ring goes round
  ok      a ring of no size is refused

5 tests: 5 passed, 0 failed.

Each file is tested as a program of its own: its tests start from the state the file leaves, and the tests of two files cannot disturb each other. A file with no test in it is not run at all, so testing a folder does not run main.zeno and blink its LED. The tests of an imported file run when that file is tested, not each time another file imports it.

Tests of one file share what the file declares, so a test that changes a var at the top of the file leaves it changed for the next. A test that needs a fresh value makes it inside itself; what a test declares is gone when it ends.

A test with a name in plain words says what is checked, and is what a failure is reported under. Functions whose names begin with test_, as in Python and Go, are a rule nobody can see in the program. Marks such as @test are a new piece of syntax for one use. Tests only in files of their own could not test anything private. test is not even a reserved word: test " at the start of a statement can mean nothing else, so programs keep the name for their own use. (Decision 10.16.)

30.6 Testing code that uses the board

Code that drives hardware can be tested on a computer too, because zeno run simulates the board: a pin remembers whether it is on, and a register remembers what was written to it (The Board). A test can drive a pin and then ask it:

heater.zeno

from board import pin

let heater = pin(5)

function control(temperature: float) {
    if temperature < 19.0 {
        heater.on()
    } else if temperature > 21.0 {
        heater.off()
    }
}

test "the heater comes on when it is cold" {
    control(15.0)
    assert heater.is_on()
}

test "it stays on until it is warm" {
    control(15.0)
    control(20.0)
    assert heater.is_on()
    control(22.0)
    assert not heater.is_on()
}
$ zeno test heater.zeno
heater.zeno
pin 5 on
  ok      the heater comes on when it is cold
pin 5 off
  ok      it stays on until it is warm

2 tests: 2 passed, 0 failed.

The simulated board says each change of a pin as it happens, which is why pin 5 on appears among the results.

30.7 Tests of the compiled program

zeno test runs the tests in the interpreter. The program that goes onto a board is another thing: the one C or LLVM makes of it, perhaps with no collector, and with numbers of a fixed width (Compiling). zeno test --build compiles each file with its tests in it, as zeno build would, runs that program, and prints what zeno test prints, line for line:

total.zeno

function total(values: list[int]) -> int {
    var sum = 0
    for value in values {
        sum += value
    }
    return sum
}

test "three numbers add up" {
    assert total([1, 2, 3]) == 6
}

test "a list counted twice" {
    let values = [1, 2, 3]
    let again = values
    assert total(values) + total(again) == 12
}
$ zeno test --build total.zeno
total.zeno
  ok      three numbers add up
  ok      a list counted twice

2 tests: 2 passed, 0 failed.

It takes what zeno build takes, such as --firmware, --no-collector, --llvm, --release and --board, so a test is held to the rules of the build it is for. The second test gives one list two names. The interpreter lets it, and so does an ordinary build. With no collector a list has one owner (Building with No Collector), so let again = values gives it away, and the test is refused as the program would be:

$ zeno test --build --firmware --no-collector total.zeno
error: `values` was given away on line 15 and holds nothing now. Use it before it goes, or give it only to what looks: a parameter without `take`
  --> total.zeno:16:18
   |
16 |     assert total(values) + total(again) == 12
   |                  ^

1 error found. No test of total.zeno was run.

No tests were run.
1 file could not be run.

A test that passes under zeno test and fails here says where the interpreter and the build part. With --board the command writes the test program for the board, such as total-tests.elf, and the board prints the same lines and the totals itself.

A few things differ on purpose. A fault of a firmware build, such as an index out of range, stops the program, as it stops any firmware program; the command names the test it was in and says how many after it were not run. And an assert must stand in the test itself, not in a function written inside the test: a failed assert leaves its test as return would, and from inside another function it would leave the wrong one.

A test the programmer writes was run only in the interpreter, but the program that is trusted on the board is the compiled one. The two are meant to agree, and Zeno’s own examples are run both ways to check it, but the place to find out where a program’s own code parts is its own tests. zeno test without --build is what it was, and a program built with zeno build has not one line more for the tests. (Decision 60.2.)

30.8 What tests leave out

There is no assert outside a test, and no code run before and after each test (a function that builds what the tests need does that). Tests do not run side by side. Under --build an assert cannot stand in a function written inside a test, and the command does not read the totals back from a board: the board prints them. (Decisions 10.21, 17.5 and 60.2.)

test "what it checks" { ... } stands at the top of a file. assert condition fails the test when the condition is false, and shows both sides of a comparison; assert condition, "text" prints the text as well. assert raises Kind { ... } checks that a block raises. zeno test runs a file, a folder or the folder it is in, and fails if any test fails. zeno test --build runs the tests in the compiled program. Builds leave tests out.

  1. Write three tests for checksum from Sized Numbers and Bits, including one where the total passes 255.

  2. Fix the average function above and run its tests again. Then add a test for an empty list. What should average do there, and what does the test say?

  3. Write a test that checks int("fast") raises a ValueError. Then change the kind to KeyError and read the failure.

  4. Make a test in one file change a var at the top of the file, and see the next test find it changed.

  5. Give the failing assert of average a message that names the list. Then run the tests of total with zeno test --build --firmware, and with --no-collector as well, and change the second test so that it passes there.
