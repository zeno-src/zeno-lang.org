How memory is managed

Memory management is the stage after compiling to C. Before it, a compiled Zeno program took memory from the machine and never gave any back. Now it carries a garbage collector: a small piece of the runtime that finds the memory the program can no longer use and frees it.

cargo run -- build --memory examples/memory.zeno
./memory
...
memory: 780027 blocks made (13222784 bytes), at most 1048574 bytes in use at once, 10 collections, 60002 blocks freed without the collector

That program asked for thirteen megabytes, a few bytes at a time, and never held more than one. --memory is what adds the last line; without it the collector works just the same and says nothing.

The last figure counts blocks that never waited for the collector. A few frees are safe at a line the compiler can point to: the old storage of a list that has just grown, the copy a for loop walks, and every value marked owned. Those are the subject of docs/ownership.md. Everything else on this page is about the blocks nobody owns. A program with no such blocks can be built with no collector at all: docs/no-collector.md.

zeno run is not affected. The interpreter is a Rust program, and Rust frees its values for it.

The files

  • src/runtime.c, the section headed "Memory": the whole collector, about 200 lines of C.
  • src/emit_c.rs: three small pieces. The top-level code moved out of main, main notes where the stack starts, and one generated function, zeno_roots, lists the top-level variables.
  • examples/memory.zeno: a program that makes far more than it keeps.

What needs memory

Numbers and bools live in C variables and need nothing. These do take memory from the machine while the program runs:

  • text that is built (a + b, an f-string, text.upper()),
  • every list, and the items inside it,
  • every object and every enum value that carries data,
  • a function written inside another, and the box of a variable they share.

Each of these is a block: a piece of memory from C's malloc. The question of this stage is when to call free.

(Memory that a program asks for itself with allocate is not on this list. The collector never looks at it and never frees it: see unsafe.md.)

The question nobody can answer in advance

function label(reading: Reading) -> str {
    let text = f"tick {reading.tick}"
    return text
}

Is text finished with when label returns? No: the caller has it now. And the caller may put it in a list, which goes into an object, which a function value remembers. In C the programmer keeps track of all that by hand, and the mistakes are famous: freeing too early (the program uses memory that is now something else), freeing twice, or never freeing.

A collector answers a simpler question, and answers it while the program runs: can the program still reach this block? If no variable leads to it, directly or through other blocks, nothing can ever use it again, and it is safe to free.

Mark and sweep

The collector here is the oldest and simplest kind. It was invented for Lisp in 1960 and is still what MicroPython runs on microcontrollers.

  1. Every block is kept in a page as it is handed out (zeno_new_block): see "Where blocks live", below.
  2. Mark. Start from the variables, which are called the roots. Whatever a root points at is in use: mark it. Whatever a marked block points at is in use too: mark that. Carry on until nothing new turns up.
  3. Sweep. Go through the pages. A block with no mark cannot be reached: free it.
roots            blocks
-----            ------
recent  ------>  [list] ---> [Reading 49999] ---> "sample 49999"
hottest ------>  [Reading 102] ---> "sample 102"

                 [Reading 7] ---> "sample 7"       nothing points here:
                 [list] ---> [Reading 3]           all four are freed

Two objects that point at each other, and at nothing else that is in use, are freed like anything else. Nothing reaches them from a root, so neither gets a mark. (This is the case that defeats the other popular method, counting references. More on that below.)

Where the roots are

A variable of a compiled Zeno program is in one of two places.

Top-level variables are C globals. The compiler knows them all, so it writes a function that hands each one to the collector. For examples/memory.zeno it is:

static void zeno_roots(void) {
    zeno_mark_words(&zeno_raised, sizeof zeno_raised);
    zeno_mark_words(&z_recent, sizeof z_recent);
    zeno_mark_words(&z_hottest, sizeof z_hottest);
}

(zeno_raised is the runtime's own variable: an error that has been raised and is on its way to an except.)

Everything else is on the C stack: local variables, arguments, and the temporaries the compiler invents. Here the collector does something blunt. It does not ask which stack slots are pointers. It reads the whole stack, from the function running now back to main, one word at a time, and asks of each word: is this the address of one of my blocks?

static void zeno_mark_stack(void) {
    void *here = NULL;
    uintptr_t low = (uintptr_t)&here, high = (uintptr_t)zeno_stack_base;
    ...
    zeno_mark_words((const void *)low, high - low + sizeof(void *));
}

&here is the address of a variable in the newest function, so it is one end of the stack. zeno_stack_base is the address of a variable in main, the other end. That is why the top-level code no longer lives in main:

int main(void) {
    void *base = NULL;
    zeno_stack_base = &base; /* the stack starts here */
    zeno_file = "memory.zeno";
    zeno_program();
    return 0;
}

Everything the program does happens inside zeno_program, so every variable it has lies between those two addresses.

One more hiding place: a pointer may be in a processor register and nowhere in memory. __builtin_unwind_init() at the top of zeno_collect makes the C compiler copy the registers onto the stack first.

Where blocks live

Memory is asked of the system 64 KB at a time, at an address that is a multiple of 64 KB: a page. A page holds blocks of one size only (16, 32, 48 ... up to 2048 bytes), and keeps at its start two bits for each block: one says it is in use, one that the collector reached it. A block bigger than 2 KB gets a run of pages of its own. Blocks have no header, so a 16-byte object costs 16 bytes.

Pages come in three sorts, which never share a page: blocks that may hold pointers (objects, lists, function values), plain blocks that cannot (text and numbers, which the collector never reads), and the rows of items of lists (see below).

"Is this word a pointer?"

zeno_mark answers it. Most words are turned away by two comparisons, against the lowest and highest addresses any page covers. For the rest, the word's top bits name a 64 KB unit of memory, and a hash table (zeno_unit_find) says which page covers that unit, if any. Then one division gives the block, and the page's bit says whether it is in use.

The same question is asked of the words inside a marked block, which is how the collector gets from a list to its items and from an object to its fields. It still does not know which fields are pointers. It does not need to.

This is called a conservative collector: when unsure, it keeps. It can be wrong in one direction only. An integer that happens to equal the address of a block keeps that block alive for nothing. It can never free something in use, as long as every pointer is somewhere it looks.

A word that points into a block keeps the block, as much as one that points at its start: C code walks through a block with a pointer. One that points just past the end counts too, but only in a page of rows: a loop over a list may be left holding a pointer past its last item and nothing else. Anywhere else the same word is the start of the next block, and counting it for the one before would keep every neighbour of every block alive. (That was a bug, found by the benchmarks: the trees program held 2.3 GB at once where it needed 130 MB. Decision 22.10.)

Following pointers without recursion

The obvious way to mark is a function that marks a block and calls itself for everything inside. On a list of 300,000 nodes, each pointing to the next, that is 300,000 calls deep, and the collector crashes the program it is serving.

Instead, a block that has been marked but not yet looked into is put on a stack of its own (zeno_marking), and one loop takes blocks off it until it is empty.

Generations

Most blocks are garbage soon after they are made, and a block that has lived through one collection usually lives through many. So most collections are small: they look only at the blocks made since the last one, the young, and take every block that lived through a collection, the old, to be still in use. Once the old have grown to twice what lived through the last full collection, the next one is full again and looks at everything.

A block is old when its "reached" bit is still set from the collection it lived through: a small collection leaves those bits as they are, and stops at an old block instead of looking inside it again. On the trees benchmark, whose long-lived tree has two million nodes, that cut the time from 11 to 7 seconds.

The danger is an old block that has since been given a pointer to a young one: nobody would look inside it, and the young block would be freed while still in use. So after each collection every full page of blocks with pointers is made read-only, with the system's mprotect. The first write to it stops the program for a moment; a handler for the signal makes the page writable again and notes that it is no longer guarded. A small collection looks inside the old blocks of every page that is not guarded, so nothing is missed. The processor keeps watch, and no line of compiled code has to remember to say that it wrote a pointer.

Pages of text are never guarded: they hold no pointers, and a file read into one by the system must not find it read-only. On a chip (--firmware), and for now on Windows, every collection is full. (0.3.0 had generations on Linux only; macOS has them again since a try jumps with a matched pair, decisions 22.11 and 22.14.) -DZENO_ONE_GENERATION asks for that anywhere.

When it runs

Collecting takes time, in proportion to what it looks at. So it is not done on every allocation. The runtime counts the bytes in use, and collects when they pass a limit. After each collection the limit becomes twice what survived.

The first limit is four megabytes (ZENO_FIRST_COLLECTION). There is a second trigger: if the system has no more pages to give, the collector runs and the request is tried again.

What it costs

  • Pauses. While the collector runs, the program does not. A small collection's pause grows with what was made since the last one; a full one's with everything in use. A control loop that must answer within microseconds should not make blocks inside the loop. Numbers, bools and fixed text never do.
  • Two bits per block, and a page header per 64 KB.
  • It leans on the C compiler. Reading the stack like this is not something the C standard describes. It works on every mainstream compiler and processor, and the Boehm collector, Ruby and MicroPython have relied on it for decades, but it is a habit, not a guarantee.
  • Now and then it keeps too much. A stale value in a stack slot that no longer means anything can hold one block, and all that block leads to. An old block that has become garbage waits for the next full collection.

docs/decisions.md, 5.7, says why this was chosen over counting references and over Rust-style ownership, and what would make the choice change; 22.5 and 22.10 why it is built as it is now.

--memory works with zeno build --llvm as well, and prints the same line.

How it is tested

A collector has one unforgivable bug: freeing a block that is still in use. The program then reads memory that belongs to something else, and fails much later, somewhere unrelated.

So every test in emit_c.rs that compares a compiled program with the interpreter is now built with -DZENO_COLLECT_ALWAYS, which runs the collector before every single allocation (63 small collections for each full one, since small ones are where a missed pointer would hide). A block that is wrongly freed is freed at the first chance, and the program prints something different from zeno run. Three more tests aim at the collector itself: one checks that a loop of garbage stays within a small amount of memory, one that a long chain, lists, objects and a function value come through many collections intact, and one that an error in flight is not lost.

Things to try

  1. Build examples/memory.zeno with --memory. Change range(50000) to ten times as many. Which of the numbers in the report grow, and which do not?
  2. Keep every reading (all.append(reading), never emptied). Watch the number of collections. Why does it rise so slowly?
  3. Compile memory.c by hand with a lower first limit: cc -O2 -DZENO_MEMORY_REPORT -DZENO_FIRST_COLLECTION=4096 -o memory memory.c -lm. What happens to the most-in-use figure, and to the running time?
  4. Make the report say how long the longest collection took. (clock() from <time.h> is enough.)
  5. Break it on purpose: in memory.c, delete the line for z_hottest from zeno_roots, compile by hand with -DZENO_COLLECT_ALWAYS, and run. What happens when the program gets to the hottest reading? This is what a missed root looks like.
  6. The table is sorted again at every collection. Blocks that survived are still in order; only the new ones are not. Sort just those and merge.
  7. malloc is a general-purpose allocator. Most Zeno blocks are 16 to 48 bytes. Give the collector its own pool for small blocks and compare the speed.
