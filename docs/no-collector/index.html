A build with no collector

zeno build --no-collector compiles a Zeno program to C that has no garbage collector in it. Not a collector that is switched off: the code is not in the file.

cargo run -- build --no-collector --memory examples/buffer.zeno
./buffer
sent 44400 samples, skipped 13 quiet frames
refused 33 frames, the first on channel 84
[3, 3, 3, 3]
4
memory: 1691 blocks made (2646299 bytes), at most 13336 bytes in use at once, no collector, 0 blocks left at the end
pool: 25384 bytes taken, in a pool of 32768
text: at most 53 bytes in use at once, in a room of 1024

The program made 1691 blocks and gave every one of them back, at a line you can find in buffer.c. Open that file and search for zeno_collect, zeno_roots or setjmp. None is there. Nor is malloc: the blocks come from a pool of a fixed size that is part of the program (pool.md).

It is a firmware build (firmware.md) with one more promise, so --no-collector turns --firmware on by itself.

Why

The collector (memory.md) is the right default. It lets you write let names = text.split(",") and never think about it again. It also has three habits that firmware cannot always live with:

  • It pauses the program, for a time that depends on how much memory is in use. A control loop with a deadline cannot plan for that.
  • It reads the C stack to find out what is still in use. That works on every mainstream compiler, and no C standard describes it.
  • Nobody can say when a block is freed, so nobody can say how much memory the program needs in the worst case.

Owned values (ownership.md) answer all three for the values that are owned. This build is what you get when every value is.

The files

  • src/emit_c.rs, the parts headed "With no collector to help" and "What a statement owns": hold, text_begin, text_end, stays, belongs. The refusals are where each kind of value is made: search for without_collector.
  • src/runtime.c: the parts between #ifdef ZENO_NO_COLLECTOR and #endif. As with ZENO_FIRMWARE, the compiler keeps one side when it pastes the runtime in (runtime in emit_c.rs).
  • src/checker.rs: Rules { one_owner }, which makes every list and object owned for this build (one-owner.md), and three small sets, fresh, made and lent, which tell the compiler which lists start life owned and which owned values are only looked at.

Where memory comes from now

With no collector, memory that is taken must be given back by a line of the program. There are exactly five ways to get memory in this build, and each has such a line.

What Where it lives When it is given back
An owned list or object the pool, a fixed array when its owner's block ends
An enum value that carries something (Wait(250)) the pool when its owner's block ends (enums-and-none.md)
A list or object that is made and given to nobody the pool when the statement that made it is over
Text built while the program runs the text room, a fixed array when the statement that built it is over
Text that is kept the pool when the variable, field or list that keeps it is done with it
An error the pool when its owner's block ends. The except that catches it is its first owner (functions-and-errors.md)
A function written where a value goes the pool when its owner's block ends, or after one line if it looks at a list or an object
Memory asked for with allocate the pool when the program says free, and not before (unsafe.md)

Numbers, bools, quantities, enum cases without data and text written in the program ("idle") need no memory at all, here as in every build.

Anything else that would take memory is refused when you build, with the line that does it:

error: this list has no owner. Give it one, as in `let items: owned list[int] = [1, 2, 3]`. `zeno build --no-collector` leaves the collector out, so nothing would free it. docs/no-collector.md lists what such a build accepts
  --> buffer.zeno:58:26
   |
58 | var refused: list[int] = []
   |                          ^

That is the whole idea of the build. It does not find leaks while the program runs. It refuses to build a program that could have one.

Owned lists and objects

In this build every list and every object is owned, by whoever received it. let xs = [1, 2] owns its list and class Task is an owned class, with no word to write. one-owner.md is the walkthrough of that, and of lists that own their items.

Nothing new happens when one is freed, and that is the point. Stage 2 already wrote a free at the end of every owner's block and on every early way out. What changes is what the free is. With a collector, zeno_free takes the block out of the collector's table and hands it to the C library's free. Here there is no table and no C library heap. zeno_alloc takes a block from the pool, one array whose size is fixed when the C is compiled, and zeno_free puts it on a list of spare blocks of its size:

block->head.asked = 0;
block->next = zeno_pool_spare[block->head.step];
zeno_pool_spare[block->head.step] = block;

pool.md is the walkthrough of the pool: how it is laid out, why it cannot break up into unusable pieces, what it costs, and how to choose its size.

Text: one statement, one fixed room

Firmware prints. print(f"sent {sent} samples") has to work, and the text it builds has to live somewhere for a moment.

It lives in the text room: one array, zeno_text_room, whose size is fixed when the C is compiled. zeno_text_top says how much of it is in use. Building text writes at the top and moves the top up. The compiler notes the top before a statement that builds text, and puts it back after:

size_t m2 = zeno_text_top;
zeno_print(1, zeno_join(5, "sent ", zeno_str_int(z_sent), " samples, skipped ", zeno_str_int(z_quiet), " quiet frames"));
zeno_text_top = m2;

Giving text back is one assignment. There is nothing to search and nothing to fragment.

A function called in the middle of a statement does the same for its own statements, above the caller's half-built text. So the room is used like a stack, and its size is the most text that can be in the making at one moment. The report's second line tells you what that was. Compile the C by hand to choose the size:

cc -O2 -DZENO_TEXT_ROOM=256 -o buffer buffer.c -lm

If a statement needs more than the room has, the program stops and says so. That is a fault, like an index past the end of a list.

Text that outlives its statement is copied. The room is emptied when the statement ends, so text that is kept cannot stay there:

print(f"channel {channel}")              # built, printed, given back
if command.strip().upper() == "ON" { }   # the same
let line = f"channel {channel}"          # `line` keeps a copy, in the pool

Whatever keeps text (a variable, a field, a list) has a copy of its own and frees it when it is done. Text is never changed once made, so a copy cannot be told from the original, and there is no rule to learn. text.md is the walkthrough: where the copies are made and freed, how a function gives text back, and what it costs. (Until that stage, keeping built text was refused.)

The compiler tracks which text is in the room with one flag on each compiled value (fixed on Val): a literal and a variable that cannot change are fixed, and everything else is in the room and is copied to be kept.

An if or while whose condition builds text takes its answer first, gives the text back, and then runs its body. A for gives it back before the first trip, and a match as soon as a case is chosen.

Errors

raise Overload(channel, peak) makes an object, and a small wrapper to carry it out of the function. raise takes the error, and the except that catches it owns it: the name after as is an owner like any other. If the block ends with the error still in that name, it is freed there, however the block is left:

if (zeno_is(zeno_caught_1, "Overload")) {
    z_Overload *z_overload = (z_Overload *)zeno_caught_1->object;
    zeno_caught_1->object = NULL;             /* the name owns the object now */
    zeno_list_append(z_refused, (zeno_slot){.i = z_overload->z_channel});
    zeno_drop_Overload(z_overload);           /* still here, so it is freed */
    zeno_error_drop(zeno_caught_1);           /* and the wrapper */
}

Inside the block the error can be read, printed and passed to a parameter that looks. It can also be kept (last = overload), put in a list, returned, and raised again (raise overload). Then the name gave it away and holds nothing, and the line that frees it frees nothing. An error can be made anywhere, not only by raise: let ready = ValueError("too hot") is an owner too. functions-and-errors.md walks through all of it. (Until that step an error could only be read inside its except.)

The error's message is often built text (raise ValueError(f"{n} is too big")), which would be gone before the except runs. So in this build the error keeps its own copy of the message, in the same block as itself.

An error that nobody catches stops the program. There is nothing to free after that.

A value between two owners

Four times, a value belongs to nobody for a moment. With a collector that does not matter. Here each needs an answer, and all four get the same one: the compiler holds the value (hold in emit_c.rs), which means that any early way out of the block frees it, just as it frees what the block's owners hold.

  1. A list being filled. [check(n) for n in range(size)]: if check fails on the fourth item, the first three are in a list that has no name yet.
zeno_list *t24 = zeno_list_new(0);
for (int64_t z2_n = 0; z2_n < t25; z2_n++) {
    int64_t t26;
    if (!z_check(z2_n, &t26)) { zeno_list_drop(t24); return false; }
    zeno_list_append(t24, (zeno_slot){.i = t26});
}

  1. An owned value on its way into a call. In join(a, b, check(n)), a and b have left their variables by the time check runs. If it fails, the failure frees them.

  2. The copy a for loop walks (decision 3.10a). A return or a failed call inside the loop frees it on the way out.

  3. A value that is made and given to nobody, as in print(count(line.split())). It belongs to the statement, which frees it when it is over, and a failure half way through the statement frees it too. temporaries.md is the walkthrough.

The first and third were small leaks to the collector in stages 1 and 2. They are now fixed in every build.

What is refused

Each of these would give a value two owners, or free one while something still looks at it. Each error names the line and says what to write instead where there is something.

Refused Why
A list, object or enum value used after it was given away (let b = a, then a) it has one owner (one-owner.md)
A function that uses a var of the function around it the two would share the variable, and nothing is shared. Use let, or an object
Keeping an item of a list of lists or of objects, which [ ] only looks at (let row = grid[0]) the list owns its items. Use it where it is, pass it to a parameter that looks, or take it out with pop() (one-owner.md)
A function that is kept and uses a var from outside it a kept function takes what it uses, and the var could be given a new value after it was taken. Declare it with let (kept-functions.md)
Replacing a list or an object that a parameter only looks at (b.items = [7, 8], where b has no take) only the owner may replace what a field holds: something else may have been lent the old value. Write take on the parameter, or return the new value
Taking an item out of a list while a for walks it (xs.pop() in for x in xs) the loop is still looking at the items, and a taken item would be freed under it (5.15e). Take them after the loop, or walk range(len(xs))
Returning or keeping what a parameter only looks at (return row, where row has no take) its owner still has it, and would free it under the new owner. Write take in front of the parameter's type, and the caller gives it away
filter on a list of lists or of objects each item kept would be in two lists, and each has one owner. Use a for loop that makes what the new list needs
Keeping an item of a list of lists or of objects that a for or a list comprehension walks ([row for row in rows]) the loop only looks at each item, which the list owns. Use it in the loop, make what the new list holds from it ([len(row) for row in rows]), or take the items out with pop()
A function with a name, written inside a function, that uses variables around it, used as a value or called from a function written where a value goes the block owns it and frees it as it ends. Write it as let add = function(...) { ... }, which has one owner (inner-functions.md)

Ten things you might expect on this list are not. A plain list or object is fine: whoever receives it owns it. A list of objects or of lists is fine: the list owns its items (one-owner.md). An enum case that carries values is fine: the value has one owner, like an object. A list, an object or an enum value that may be none is fine: none owns nothing (enums-and-none.md). A named function used as a value (items.reduce(add, 0)) is fine: it takes no memory. A function written where a value goes is fine: it has one owner. An error that is kept or raised again is fine: so does it (functions-and-errors.md). Text that is kept is fine: the keeper has a copy (text.md). A list that is made and only looked at is fine, whatever makes it (x in [1, 2], count(line.split()), len(a + b)): the statement frees it. And a list that a for loop walks is fine (for pin in [2, 3, 5], for word in line.split(), for ch in text): the loop frees it. Both are in temporaries.md.

Since 0.8.0 four more are fine. A function that is kept takes what it uses from outside it (kept-functions.md). A list or an object can fill a type parameter, as in Stack[Frame] (generic-owned.md). And a dict of lists or of objects owns its values, as a list owns its items (dict-owned.md). And a list of numbers that may be none owns a block of the pool for each number (none-list.md).

All ten rows are by design: with no collector nothing is shared, and what a block owns ends with the block. A list of int or none was a row, a limit of version 0.1 (decisions, 11.2), until 0.8.0.

A program that every build refuses is not on this list; those are in compiler.md, each with its reason. The test what_a_build_with_no_collector_refuses_says_so holds both lists to what the two compilers do: each row is refused, in the words its page shows, and a row that is missing from a page, or a page that lists what the compilers take, fails it. And tools/refused.py builds each of several hundred small programs, one operation on one type, six ways: a refusal that neither page lists, or a program that C and LLVM do not treat alike, fails it, and the test reads what it found (decision 56.19).

What this does not claim

  • Memory is still taken and given back while the program runs. It comes from a fixed pool and not from the heap, so MISRA C:2012 Rule 21.3 (no malloc, calloc, realloc or free) is met. Directive 4.12 is wider: it is against dynamic memory of any kind, and a pool is still that. pool.md, "What this does not claim", says what the pool does and does not answer.
  • It does not bound memory for you. A loop that appends to an owned list for ever fills the pool, and the program stops there. --memory tells you what a run needed.
  • The text room is a fixed size that you choose. Too small, and the program stops at the statement that overflowed it.
  • The rest of the list in firmware.md stands: printf and exit, variable argument lists in the runtime, the GCC builtins for checked arithmetic, and the forward goto.

The same, through LLVM

cargo run -- build --llvm --no-collector --memory examples/buffer.zeno

zeno build --llvm --no-collector is this design written in LLVM IR. An owner is a slot that is set to null when it gives its value away and dropped where its block ends. The text room's top is a global the IR loads before a statement that builds text and stores back after it. An except owns the error it caught, and drops it if it still has it when the block ends. The runtime file beside the IR is the one from this page, and what is refused is refused in the same words. llvm.md, "Owned values" and "With no collector", walks through the IR.

The two builds do not only print the same. They make the same number of blocks, hold the same number of bytes at most, and fill the text room to the same height, and the tests require it.

How it is tested

Every test program for this build (no_collector_as_interpreter in emit_c.rs) is checked four ways:

  1. It prints exactly what zeno run prints.
  2. Its memory report ends with 0 blocks left at the end. With no collector, a block that no line frees is never freed, so this number is the test.
  3. The C file does not contain zeno_collect, zeno_roots or setjmp, nor malloc, calloc, realloc or the library's free.
  4. The same program still agrees with the interpreter in the two builds that do have a collector.
  5. Built through LLVM with no collector, it prints the same, and its memory report is the same as the C build's, line for line.

The programs aim at the hard places: an error raised inside a loop over a list, inside another except, half way through filling a list, and while owned values are on their way into a call; return, break and continue out of except blocks; and two thousand trips round a loop that builds text, which must leave the text room as it found it. A table of 14 small programs checks that each refusal says what it should, and that each of them still builds where there is a collector.

They were also run by hand with gcc and clang at several optimisation levels, and, while memory still came from the heap, under AddressSanitizer with its leak check on. pool.md lists the tests of the pool itself.

Things to try

  1. Build examples/buffer.zeno with --memory, then with --no-collector --memory. The second makes fewer blocks. Which ones are gone? (Look at where the text went.)
  2. In buffer.zeno, take the word owned off refused and build with --no-collector. Nothing changes: in this build the list has one owner either way. Then keep an error: var last: Overload or none = none and last = overload in the except. Build with --memory. Which line of buffer.c frees the error now?
  3. Compile buffer.c by hand with -DZENO_TEXT_ROOM=32. Which statement stops the program? What is the smallest room it runs in, and does the report agree?
  4. let line = f"plain text" copies the text into the pool, though nothing in it is built. Find where format_string makes its value, and when every part is a literal make it the literal itself. How does the report for such a program change?
  5. This exercise used to be "replace calloc and free with a pool". That is done (pool.md), so here is what is left of it: print, from zeno_memory_report, how many blocks of each size were ever cut from the pool. Which sizes does buffer.zeno ask for, and which size holds most of the pool?
  6. print(42) builds the text "42" and then prints it. Give the runtime a zeno_put_int that prints a number with no text room, and make the compiler use it when print has one argument.
  7. look([1, 2, 3]) used to be refused, where look has a parameter xs: list[int] that only looks. It builds now: find the line in the C that frees the list, then make look fail (give it a raises) and find the second line that does. temporaries.md says how both got there.
  8. raise e inside except ... as e used to be refused. It is a move now. Write one, find the zeno_error_of call in the C, and explain why the old wrapper can still be freed on the next line.
